## 2. SCA NavFn tolerance 问题最终定性

此前 SCA odom-only Nav2 重构中曾设置：

```text
NavFn tolerance = 0.1 m
```

而：

```text
AIMAPP 原始 NavFn tolerance          = 0.5 m
SCA cognitive node influence radius = 0.5 m
```

因此形成了运动执行层与认知节点空间尺度之间的不一致。

典型失败目标：

```text
(-0.578, 2.180)
```

诊断结果：

```text
目标中心距最近已观测障碍约 0.095 m
0.1 m 范围内：无安全替代终点
0.5 m 范围内：存在安全替代终点
```

因此将 SCA NavFn tolerance 从 `0.1 m` 修正为 `0.5 m`，属于修复 SCA Nav2 重构过程中引入的配置尺度不一致，而不是修改 SCA 高层主动推断算法。

注意：修改的是 NavFn planner tolerance；`xy_goal_tolerance` 没有因此统一改成 0.5 m；也不能把历史 AIMAPP/SCA 的全部路程差异归因于该问题。

## 3. AIMAPP model.pkl 磁盘膨胀根因

在线核对 AIMAPP pinned 源码后确认，官方代码每个 step 都保存完整模型：

```text
save_step_data(...)
    -> step_N/
    -> model.pkl
```

失败 step 同样可能保存完整模型。此外 AIMAPP 运行目录还维护：

```text
tests/<run_id>/model.pkl
```

因此此前长跑约 151 step 即接近 50 GB，主要原因是每个历史 step 都保留一份完整 `model.pkl`。

正式处理原则：

```text
不修改 AIMAPP 官方算法源码
不改变模型运行语义
只在 experiment harness 外部控制历史快照保留
```

## 5. 第一个关键坑：不能用 mtime 判断最新模型

retention 第一版使用文件修改时间判断“当前最新模型”。假数据中实际最大 step 为 `step_151/model.pkl`，但最后人为创建了 `step_51*/model.pkl`。由于其 mtime 更新，第一版程序误把 `step_51*` 当作最新进度，并删除了真正的 `step_151`。

错误结果：

```text
step_50
step_51*
step_100
step_150
```

最终修复为：

```text
primary key   = step number
secondary key = mtime
```

重新测试：

```text
step_50
step_100
step_150
step_151
RETENTION TEST: PASS
```

固定结论：AIMAPP 实验进度必须以 `step_N` 中的 N 为准，不能用文件时间替代实验 step。

## 9. no-progress watchdog

原 formal runner 已有：

```text
RUN_TIMEOUT_SEC = 14400
```

即 4 小时 absolute timeout。

当前新增：

```text
NO_PROGRESS_TIMEOUT_SEC = 1800
```

即连续 30 分钟没有高层 action 进展时，将当前 run 记为 `no_progress_timeout` 并停止，同时保留失败证据和 `progress_watchdog.log`。

该机制属于实验基础设施保护，不是算法终止条件、论文性能指标或成功判据。

## 10. 第二个关键坑：Nav2 success 不能代表 SCA 高层进度

watchdog 初版对 SCA 使用 `Nav2 goal succeeded` 作为进展信号。重新检查 SCA 后发现：

```text
STAY action
    -> SCA 本地直接完成
    -> 不会发送 Nav2 goal
```

因此：

```text
Nav2 goal succeeded 数量 != SCA completed high-level action 数量
```

若连续出现 STAY，模型实际上正常推进，但 watchdog 可能错误认为“无进展”。所以该方案已经放弃。

## 14. 第三个关键坑：ROS setup 与 set -u

本日尝试直接运行测试时出现：

```text

COLCON_TRACE: 未绑定的变量
```

原因是 ROS 2 Humble setup 脚本可能访问尚未定义的可选环境变量，而 shell 当时启用了 `set -u`。

ROS setup 前应使用：

```text
set +u
source /opt/ros/humble/setup.bash
```

不要在 setup 阶段强制 nounset。
